# 百年茶緣網站開發規劃(兩週 MVP 版)

適用情境:比賽提案用 demo(現場操作講解,不接資料庫)、2 人團隊、七個章節分開做最後合併、使用 Codex 開發、GitHub 協作。技術為純 HTML/CSS/JavaScript,風格是 HD-2D 氛圍像素風,一律以已完成的第一章為準。

**2026-11-17 更新,依正式版儲存庫調整。** 正式版儲存庫:https://github.com/jpgggg0850093281-hash/bainian-chayuan-release ;第一章試玩:https://jpgggg0850093281-hash.github.io/bainian-chayuan-release/ 。實際檔案結構與規範以儲存庫內的 README.md、AGENTS.md、STYLE.md 為準,本文件與它們衝突時,以儲存庫文件為準。

## 一、協作方式(GitHub)

兩人分開做不同章節,靠 GitHub 的分支與 Pull Request 合併。

- main 只放可運作的版本,GitHub Pages 從 main 發布(以實際設定為準)。
- 一章一個分支,從最新的 main 建立,例如 chapter/02-water-gate;修正用 fix/…。
- 每完成一個可測試的更新就提交並推送到自己的分支;完成後開 Pull Request,由組員驗收後再合併。不直接推送到 main。
- 只改自己章節的檔案。共用檔案(主角、核心程式、共用樣式、任務面板、存檔流程)要改時保持最小,並在合併前通知組員確認。
- 每次更新都在 README 的「變更紀錄」補一筆(格式見第九節)。
- AGENTS.md 是給 AI 協作者的規範,Codex 會讀;之後若用 Claude Code,可放內容相同的 CLAUDE.md。
- 儲存庫目前是公開的;若不想提早公開美術與內容,可改成 Private,再加組員為協作者。

## 二、技術與 Demo 範圍

| 項目 | 做法 | 說明 |
| --- | --- | --- |
| 前端 | 純 HTML + CSS + JavaScript | 沿用正式版儲存庫現有結構,不引入框架 |
| 遊戲呈現 | HD-2D 氛圍像素場景 + 主角自由走動 + 互動點 + 特寫畫面 | 走到互動點 → 進入特寫 → 操作 → 回場景回報 |
| 小遊戲 | DOM 互動或輕量 Canvas | 配對、分類、排序、閥門操作等,不用遊戲引擎 |
| 操作 | 滑鼠與手機觸控 | 觸控目標約 44 像素以上,直式與橫式都能玩 |
| 雙語 | 繁中與日文 | 文字放語系檔,位置以儲存庫為準 |
| 資料 | 靜態資料,不接資料庫 | 存檔沿用第一章既有流程 |
| 部署 | GitHub Pages | 合併進 main 後自動更新 |
| 字型 | 與第一章相同(修正後為像素字型) | 需支援繁中與日文,確認授權 |

**Demo 範圍(提案講解用,建議)**

- 七個章節各自做,每章至少一個可操作的場景互動。
- 現場報告約 10 分鐘,操作約 3 分鐘:以第一章完整流程為主,再用快速跳轉展示其他章節的代表互動。實際路線等各章完成後再排。
- 快速跳轉(?scene=…&step=… 或除錯面板)讓現場不必從頭玩;各章要加自己的跳轉設定。
- 備案:每個現場操作的畫面都準備截圖,網站出狀況時切到簡報繼續講。
- 不做:登入、帳號、資料庫、核銷驗證、後台。永續行動頁、核銷流程、後台數據以示意圖在簡報呈現。

## 三、頁面與功能清單

**P0(必做)**

1. 首頁:標題、玩法簡介、開始遊戲、中日語言切換
2. 沿用第一章的存檔與任務面板
3. 茶園主畫面:四項指標(經營資金、茶葉品質、環境健康、地方共好)與章節進度
4. 七個章節(每章至少一個可操作互動,規格見第四節)
5. NPC 對話系統:頭像、名稱、逐字顯示、選項分支
6. 紀念幣收藏頁:點開可讀每枚幣對應的歷史故事
7. 日式扭蛋機:集滿七枚解鎖、次數與獎品上限
8. 結算頁:四項指標成果、問卷連結、茶文化工作坊報名連結

**P1(能做就做,做不出來就用示意圖)**

9. 永續行動頁:環保杯核銷碼輸入、青年茶鄉故事(影片或圖文 + 小問題)
10. 簡易後台:啟動人數、完成率、核銷紀錄,對應企劃書 KPI
11. 資料來源與關於頁:列出歷史與時事資料來源

**P2(有時間再做)**

12. 背景音樂與音效、成就、分享圖片、日本玩家的純線上額外任務

## 四、七章遊戲規格(開發用)

| 章 | 主題 | 玩法形式 | 開發重點 |
| --- | --- | --- | --- |
| 1 | 雨後的第一壺茶(已完成) | 茶園走動、採茶、老茶寮泡茶、水車水閘 | 風格與做法的標準樣板 |
| 2 | 氣候變遷 | 情境選擇(灌溉、保水、栽培調整) | 選項對應指標變化 |
| 3 | 人口老化 | 情境選擇(青年招募、培訓、設備、合作) | 選項系統 + 茶農故事彈窗 |
| 4 | 生態探索 | 圖片配對、簡易分類 | 小遊戲元件 |
| 5 | 環境保護 | 閱讀整理資料 + 多方立場 + 決策(名間焚化爐議題) | 多位 NPC 立場、無標準答案 |
| 6 | 百年茶緣尋寶 | 時間軸排序、圖片配對解謎 | 小遊戲元件、收藏品解鎖 |
| 7 | 百年茶緣祭典 | 成果回顧 + 扭蛋 | 結算畫面、扭蛋動畫 |

**通用機制**

- 每章 5 至 10 分鐘;章節依序解鎖,不要求連續七天登入,玩家可隨時回來繼續。
- 每章完成後發一枚紀念幣。
- 章節內容、對話、選項全部做成資料檔(JSON),程式只負責讀取與呈現,這樣新增或修改內容不用動程式。
- 選項資料格式範例:

```
chapter: 2
choice: id, textKey, effects { funds: -10, quality: 5, env: 10, community: 0 }, feedbackKey
```

**內容與互動規則**

- 互動流程統一:走到互動點 → 進入特寫 → 操作 → 回場景回報。例如水車水閘:走到水閘旁、進入特寫、操作閥門、觀察水流方向、回場景回報。
- 每章先寫好開場、玩家要完成的動作、完成條件、如何接到下一章,並交分鏡給負責人確認後再接進遊戲。
- 乾茶葉是深褐到近黑的捲曲短條,鮮採嫩葉才是綠色。
- 水流方向與水車轉向要一致(水從左上落下時水車逆時針轉,出水向右下流)。
- 手臂、人物動作只做平移與旋轉,不拉伸圖片。

## 五、資料處理(demo 不接資料庫)

- 章節內容、選項、NPC 對話:放在靜態資料檔(位置以儲存庫為準)。
- 玩家進度(章節、四項指標、紀念幣、扭蛋次數):沿用第一章既有的存檔流程(實際做法以儲存庫為準)。
- 不做資料庫、登入、核銷碼驗證。
- 簡報說明用:若企業方實作,可再接資料庫,資料表可設計為 players、progress、coins、gacha\_chances、redeem\_codes(核銷碼與使用上限)。
- 隱私:盡量不蒐集個資;獎品寄送資料以外部表單另外收。

## 六、章節分工與流程

第一章已完成,是標準樣板。第二到七章採認領制,誰有空誰做:在 GitHub Issues 每章一個 Issue,開工前把自己設為 Assignee,一次只認領一章。建議第七章最後一起做(需要前六章的紀念幣)。每章的流程:

1. 依比賽大綱寫章節內容(開場、動作、完成條件、接到下一章)。
2. 交分鏡給負責人確認。
3. 從最新的 main 開自己的分支。
4. 實作並在手機與電腦上測試。
5. 在 README 的「變更紀錄」補一筆。
6. 開 Pull Request,附測試結果與和第一章並排的截圖,由組員驗收。
7. 合併進 main,通知組員 git pull。

## 七、美術與風格規格

- 風格以第一章為準:像素顆粒、角色比例、光影(暖色、光源左上)、色票、字型、對話框、互動提示都要一致;畫面中任何兩個物件的像素顆粒大小相同。
- HD-2D 指的是氛圍,不用 3D、真實光照或平滑漸層;房屋、石牆、茶叢、水面用清楚的方形色塊畫出層次,保留可辨的像素邊緣。
- 主角使用定稿(深棕蓬鬆短髮、無帽子、深藍外衣、斜背竹籃、棕黃長褲、棕色靴子),沿用既有素材與走路動畫,不重畫。
- NPC:茶農後代、沼田市青年、地方文化工作者、新井耕吉郎(真實歷史人物,形象以可查證資料為依據)、導覽 NPC。
- 新圖片放進 assets/,以章節或場景名稱命名(小寫英文加連字號),檢查相對路徑與大小寫;使用透明背景 PNG 原檔,不用截圖。
- 不可直接使用網路圖片;AI 生成的圖要處理成與第一章相同的像素密度與色票。
- 圖片需預載,切換場景與開啟特寫時不可出現空白面板。

## 八、風險與取捨

- **時間緊**:以 P0 為準;音效、後台、永續行動頁延後或用示意圖。
- **名間焚化爐議題為真實爭議**:內容要有可查證來源與多方立場,避免單一立場,上線前兩人互相核對。
- **遊戲數值不是農業建議**:結算頁加一段簡短說明。
- **獎勵防濫用**:核銷碼次數上限、每人扭蛋次數上限;日本玩家以線上任務取得額外機會。
- **授權**:字型、音效、圖片都確認可用於比賽與公開網站。
- **雙語一致**:日文內容請母語者校對,可考慮請合作的日本大學協助。

**已知問題(第一章修正中,新章節不要沿用):** 手套或小圖的像素比背景粗、道具初始狀態沒有重設(茶杯未倒茶就有茶湯)、UI 使用平滑字型、水壺遮住角色的臉、互動目標對比不足。

## 九、變更紀錄格式與組員開工

```
### YYYY-MM-DD HH:mm(UTC+8)|第 X 章:章節名稱
- 作者/分支:組員名/chapter/xx-scene-name
- 版本:填版本號,或在合併後補上 PR 編號
- 改動:新增或修改了哪些場景、互動、圖片與檔案
- 原因:這項改動解決什麼問題,或對應大綱哪一段
- 測試:手機觸控、電腦操作、圖片載入、任務完成與返回場景的實測結果
- 回復方式:合併後可回復此 PR;如有存檔格式變更,寫明如何恢復
```

變更紀錄放在 README,最新的在最上面,保留舊紀錄;時間用系統時間,測試只列實際做過的項目。

組員開工時,把「給組員的 Codex prompt」填好負責章節、組員與故事地點後貼給 Codex。這份 prompt 會在確認儲存庫實際結構後定稿,定稿後建議一併放進儲存庫的 docs/。
